# FORAGE

FORAGE is a Streamlit analytics app about household food demand and waste, built for a Fundamentals of Data Science project. It shows the whole workflow on four sources it never mixes: data quality checks, exploratory statistics, waste and expiry analysis, chronological forecasting with baselines, and explainable recommendations.

The project is framed by UN SDG target 12.3: halve per-capita food waste at retail and consumer level by 2030.

## Data sources

| Source | What it is | Rows | Supports |
| --- | --- | --- | --- |
| Demo data | Synthetic household records: 20 foods × 365 days (2025), generated by `src/generate_data.py`. For illustration only, not real evidence. | 7,300 | Everything, including waste, expiry and purchase quantities |
| My Data | Records you add or import yourself, stored locally in `data/my_food_data.csv` (git-ignored) | yours | Same as demo once there is enough history |
| M5 (Walmart) | Retail unit sales from the M5 Forecasting dataset: store CA_1, the 100 best-selling FOODS items, last 180 days (28 Oct 2015 – 24 Apr 2016) | 18,000 | Statistics, forecasting, demand trends. **No waste, stock or expiry.** |
| Instacart | Market Basket Analysis orders from users 1–2,000 | 313,404 order lines, 31,749 orders | Statistics, reorder behaviour. **No quantities, dates, waste or expiry.** |

Choose the source in the sidebar. Every page states which source it is showing. When a source cannot support an analysis, the page says so instead of estimating a value. For example, waste is not available for M5 or Instacart, and forecasting is not available for Instacart, which has no calendar dates.

## Pages

| Page | Purpose |
| --- | --- |
| Overview | Headline figures for the selected source and what each source supports |
| Data Quality | Cleaning steps with rows removed per rule, the stock-balance check, a column profile and IQR outliers (flagged, not removed) |
| EDA | Descriptive statistics (mean, median, mode, std, min, max, Q1, Q3, IQR), a category frequency table, a correlation heatmap with a one-line reading, and the main patterns |
| Waste & Expiry | Waste rates by food and category, stock expiring within 3 and 7 days, waste rate against shelf life, and expiry-driven waste by category |
| Forecasting | Models and baselines on a held-out later period: a metrics table, actual vs predicted, and what the result means |
| Recommendations | Purchase quantities (demo and My Data), rising and falling demand (M5), and dependable repeat purchases (Instacart), each with its formula |
| My Data | Add, import (with column matching and quality checks), edit and delete personal records |

## Definitions

- **Stock balance:** purchased = consumed + wasted + remaining (within ±0.011 for rounding). Rows that fail are removed during cleaning and counted.
- **Waste** is the recorded quantity wasted. It is never computed as purchased − consumed, because that would count food still in stock as waste.
- **Waste rate of a food** = total wasted ÷ total purchased × 100. Quantities are summed only within a food, so units (kg, L, dozen, loaf, pack) never mix. Category and overall rates are the mean of the food-level rates; the pooled rate is shown for reference.
- **Expiry-driven waste:** the data does not record why food was thrown away, so waste on foods with a shelf life of 7 days or less is treated as expiry-driven.

## Forecasting method

- The target is next-day consumption (demo, My Data) or next-day unit sales per item (M5).
- These are **one-step-ahead** forecasts. Lag and rolling features are shifted within each food or item, so the prediction for day *t* uses actual values up to day *t−1*.
- The split is chronological: the first 80% of dates are used for training and the last 20% for testing. Scaling and encoding are fitted inside the pipeline on the training rows only. Missing M5 prices are filled with the training-period median.
- Candidates are two baselines (yesterday's value, 7-day moving average), Linear Regression and Random Forest. All are scored with MAE, RMSE and R² on the same held-out period.
- The selected model is the one with the lowest test MAE. It is never fixed in code, and the recommendations use the same selection.

## Architecture

```text
app.py                  Entry point: page config, sidebar (navigation + data-source selector), routing
views/                  One file per page (run by st.navigation)
  overview.py  data_quality.py  eda.py  waste.py  forecasting.py  recommendations.py  my_data.py
  common.py             Page header, source label and "not available" states shared by pages
  auth.py               Supabase sign-in screens, shown only when AUTH_ENABLED = True in app.py
ui/                     Presentation helpers
  theme.py              Chart colour tokens for light and dark mode, and a small amount of CSS
  charts.py             Altair builders: bar, line, histogram, scatter, correlation heatmap
  components.py         KPI row, section headings, empty states, table formatting
services/data.py        Source registry, cached loaders (st.cache_data) and cached model results
src/                    Analysis logic: pure functions, no Streamlit, all unit-tested
  clean_data.py         Raw → cleaned demo data, with a per-rule removal summary
  data_quality.py       Quality report, column profile, IQR outliers, safe cleaning for imports
  stats.py              Descriptive statistics, frequency tables, correlations
  waste.py              Waste rates, balance check, expiry analysis (refuses sources without waste)
  prediction.py         Demo features, chronological split, model evaluation and selection
  m5_forecasting.py     M5 features, price imputation, evaluation
  recommendations.py    Next-day purchase plan (demo) and personal recommendations
  personal_data.py      Local personal-record store
  dataset_loader.py, schema_mapper.py   CSV import and column matching
  real_data_processor.py                Builds the bounded M5/Instacart extracts from raw downloads
  generate_data.py, analysis.py          Demo-data generator and a command-line EDA script
tests/                  pytest suite
.streamlit/config.toml  Light and dark theme, one accent colour, Inter, chart palette
```

## Run the app

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

Streamlit follows the operating system's light or dark preference and opens in light mode otherwise. You can switch themes under Settings in the app menu.

The M5 and Instacart pages need the local extracts. Place the raw downloads under `dataset/` and run:

```powershell
python src/real_data_processor.py
```

Raw downloads, extracts, personal records and generated outputs are git-ignored. When an extract is missing, its pages say how to build it.

## Run the tests

```powershell
python -m pytest
```

The 54 tests cover:

- **Cleaning:** duplicates, missing values, unparseable types, impossible values, unbalanced rows, outliers that are kept, and no invented expiry dates.
- **Statistics:** known values, zero vs missing, mode ties, frequencies and correlations.
- **Waste:** ratio-of-totals rates, zero purchases, unit-neutral averages, the balance check, expiry windows, and refusal to compute waste for M5 or Instacart.
- **Forecasting:** shifted lags, a rolling mean that excludes the current day, the chronological split, held-out metrics, best model chosen from results, and recommendations using that model.
- **Leakage:** one test multiplies every target after the cutoff by 100 and checks that the training data and the fitted model are identical. Another checks that the scaler is fitted on training rows only.

Command-line versions of the analysis are also available: `python src/clean_data.py`, `python src/analysis.py`, `python src/prediction.py` and `python src/recommendations.py`.

## Limitations

- The demo data is generated. In it, waste is a random share of the unused purchase and does not depend on expiry, which is why foods with long shelf lives show the highest waste rates. Real household data would be expected to show the opposite pattern.
- R² on the demo data is pooled across foods with different typical quantities, so part of it reflects differences between foods rather than day-to-day accuracy.
- The M5 and Instacart extracts are bounded subsets (one store, 100 items, 180 days; 2,000 users), so they are not representative of the full datasets.

## Deployment

Deploy on Streamlit Community Cloud with main file `app.py` and branch `main`. No secrets are needed while `AUTH_ENABLED` is `False`. Never commit `dataset/`, `data/real/`, `data/my_food_data.csv`, `.streamlit/secrets.toml`, `.venv/` or any credentials.
